# 需求合理性审查参考 · 用户体验需求评估默认模式

本文件是**专业判断依据及输出细化规则**，不是执行工作流。仅在需求复杂、需区分多个原则或需要反例时读取。无需每次都逐条输出所有专业领域和检查项目。

**服务目标与审查深度：** 面向用研、产品、设计及相关角色，帮助把需求目标、用户任务、体验机制、关键假设和可选方案讲清楚，兼顾用户体验知识普及。普通讨论只需做到核心推理自洽、科学概念使用准确、没有无依据的因果或实测断言；不必进行完美穷尽的专业解析。专业反例、标准条文与原始证据只在足以改变判断或涉及重要风险时深入。适当解释术语，使非用研背景的读者也能理解。

## 1. 判断对象

必要时拆分需求中的目标、固定手段、禁止事项和结果保证，确定用户、任务、设备/环境及控制权。区分四种信息：**用户陈述、已核实事实、有依据的条件性推断、未知**。单一清晰需求直接判断，不为了完整流程拆分。

按关联性选择视角：
- **用户研究**：态度与行为、概念与测量、样本代表性、因果与相关、NPS/满意度指标是否被误读，结论能否由证据支撑。
- **人因工程/认知**：感觉与注意、认知和身体负荷、可达性、疲劳与情境差异、操作失误及安全影响。
- **交互可用性**：识别、理解、导航、反馈、一致性、错误预防和恢复、操作成本、任务可完成性。
- **通用设计/包容性**：不同能力和环境下的信息可感知性、可操作性、灵活性与容错。通用设计原则不自动等于某项已生效的强制规范。

**方法学要求：** 重要判断必须能追溯到“用户与任务情境 → 选用的框架/人因交互原则 → 作用机制 → 证据与最强反例 → 结论”。按问题择一两种工具：信息缺口用 **5W1H**；产品方案与用户真正任务不一致用 **JTBD**；功能质量属性用 **Kano**（无目标用户数据只可列为假设）；心理需要可谨慎参考**马斯洛**（不得据此作固定层级或优先级结论）；复杂操作风险使用**任务分析与相关人因/交互原则**。方法名称不是证据；简单问题不强制显式列出框架。适用条件和局限见 [method-selection.zh-CN.md](method-selection.zh-CN.md)，**仅在方法选择影响判断时读取**。

### 优先分清两类问题：需求是否合理，原因是否已知

“分析用户为何看不清文字”“分析在线功能为什么不再使用”是**体验问题分析诉求**，通常合理；原因未证实并不影响分析诉求本身的合理性。先问**哪些用户、在何种任务和情境下，出现怎样的感知/行为痛点，影响了哪些体验目标**。再提出少量相互竞争、能改变解释的用户体验机制；不要直接铺开面板参数、实验设计或统计分析。若要求事先证明特定归因、保证改善，则**单独评估这条强制结论或方案是否合理**。

规范符合性与真实任务可读性不是同一概念；舆情声量与用户群体发生率不是同一指标；低频任务完成后不再打开功能也不必然是流失痛点。把这些区分讲给用户听，胜过罗列工具和术语。

## 2. 三类结论与证据门槛

| 结论 | 成立条件 | 需要说清什么 |
| --- | --- | --- |
| **合理（内部类别）** | 目标与手段可相容，未发现明确原则冲突 | 对外可说“目标成立，可以继续推进讨论”，并说明依赖的条件；不代表实测通过或审批通过 |
| **需要核实或调整（内部类别）** | 信息、指标、情境或指定方案仍有关键缺口，尚可核实或修订 | 对外说清“哪部分可取，哪部分需确认/调整”；如果目标本身也缺乏依据，应说“目前还不能判断”，不预设方向合理 |
| **原则性问题已成立（内部类别）** | 相同对象、时间、维度和约束下可证明矛盾；已确证的无效推断硬充事实；明确要求造假、隐瞒重大伤害；或经核验违反确实适用的强制义务 | 对外明确具体不可接受的要求，以及为何不宜按现有方案推进；不把单纯证据不足升级为错误 |

**对外结论采用自然中文，而非标签翻译。** 不要默认输出“总体判断：有条件合理”，也不建议统一写“有条件通过”，因为这里不是需求审批。根据实际情况说明**目标是否成立、指定手段是否适宜、关键前提是否有证据**。例如：“提升语音交互能力的方向合理，但将语音设为主要交互方式仍需明确任务与驾驶情境”；“当前信息不足，暂不能判断是否适合替代触控”；已证实原则冲突时写明“不应按现有方案推进”。三类判断仅用于内部归档和推理，不强迫对外文字与类别逐字对应。速览表中每一行也应用“可能增加纠错负担”“适用条件待确认”等具体判断替代套话。

**关键反例先行**：能否通过不同操作条件、另一种目标定义、已有合法资源或可选交互实现？若可以，不能轻率判为原则性错误。未知不等于错误；“很难”“低预算”“上级要求”“研究者不喜欢”均不构成错误证据。

**风险与合理性分轨**：缺少足够证据证明风险确实存在，不得断言已经造成伤害。但对于潜在严重安全风险，可以在判断仍待核实的同时建议**暂缓受影响的操作**，直到必要风险核查完成；不必等正式认定违法才提示暂停。

法规/标准判断必须核实版本、市场、适用主体、具体场景及条款。未核实就写“待核实”，不编造编号、阈值或“强制违规”结论。

## 3. 渐进式输出：关键维度速览 → 按需展开

**首层的目标是让用户迅速掌握需求的核心矛盾和下一步该看哪一部分，而不是代替用户阅读一份完整分析报告。**

- **整体结论**：一两句话说明分析诉求/需求是否合理，哪一部分仍有条件；不要把归因未知等同于分析问题不合理。
- **维度速览**：多因素问题按需选择 **2–4 个、最多 5 个**最能改变结论的维度，按“**编号与维度｜快速评估｜最重要的用户体验依据或待核实条件**”三列表格展示。一行一项；判断须落在用户/任务/痛点和人因交互机制，不能只列标签。简单单一问题仍可用一段话，不必强制表格。维度不是固定的“用户/认知/交互/指标”四项，而应因任务、群体、情境、目标冲突而调整。
- **判断措辞**：根据实际对象写“目标合理、手段待确认”“目前无法判断”“存在潜在风险”“原则冲突已成立”等具体句子，不机械输出“有条件合理/有条件通过”；**潜在风险≠已经发生，证据不足≠需求错误**；不要把定性状态伪装成经过量化的评分、置信度或严重等级。
- **首层结尾**：若有必要，补充一句需求层面的修订/判断条件，然后提供“**回复「展开 2」「展开 1 和 3」「展开全部」**”等**文本分支指引**。仅在宿主真正支持时才使用交互控件；普通 Agent Skill 不承诺按钮或可点击折叠组件。
- **默认不展开**：如果宿主不支持真实的折叠/展开控件，首层呈现后即停止，由用户下一轮明确指定分支。不得模拟可点击按钮、自动补全细节或擅自展开全部。若用户仅说“展开”且有多个维度，简短询问编号而非替用户选择。
- **分支展开**：仅回答用户选中的编号/名称，保留原需求、任务与证据边界；细化该维度的体验机制、适用条件、可能影响结论的关键反例（如有）、证据状态及最少必要事实。不要重发完整总览、自动延伸未选分支或编写研究/实验/数据建模/工程实施流程。用户说“展开全部”也仅深化已有需求合理性维度。新增事实确实改变判断时解释变化依据；新需求重新生成维度。
- **风险例外**：可能造成重大安全影响的事项必须在首层简明提示，不能仅藏在后续展开中。
- **人工核查提示**：仅当建议依赖未验证的关键事实、具体标准条款或可能导致较高后果时，在相关判断附近简短提醒自行核查；无需在每个维度都附加“AI 可能出错”的通用声明。

5W1H、JTBD、Kano、任务分析等方法多数情况下用于形成判断，而非作为默认表格行或正文标题。输出紧凑、可浏览、可追溯，而不是增加一份新的固定检查表。

### 泛化输出参照（假设情境，非真实研究结果）

**场景 A：文字辨识投诉增加，但设计规则核查通过**

**判断：分析诉求合理，根因尚未确认。** 关键在于真实阅读任务是否受影响，而不仅是静态设计指标。

| 维度 | 快速评估 | 主要依据或未知 |
| --- | --- | --- |
| **1. 用户与阅读情境** | 待明确 | 哪些用户、阅读距离、任务和环境下出现困难 |
| **2. 视觉可读性与负荷** | 潜在问题 | 字形、对比和观看条件可能增加辨识成本，尚未实证 |
| **3. 舆情解释效度** | 证据不足 | 投诉数量不等于用户群体发生率 |

**可展开（仅限需求合理性）：** 回复「展开 1 / 2 / 3」。

**场景 B：在线功能留存被认为过低**

**判断：分析诉求合理；“留存低就说明体验失败”尚不成立。**

| 维度 | 快速评估 | 主要依据或未知 |
| --- | --- | --- |
| **1. 用户任务与复用动机** | 需澄清 | 低频需求完成后不回访未必是失败 |
| **2. 首次体验与任务障碍** | 潜在问题 | 是否因理解、操作成本或信任障碍而放弃任务尚未知 |
| **3. 留存指标的适配性** | 证据不足 | 指标周期能否代表真实任务复现未确定 |

**可展开（仅限需求合理性）：** 回复「展开 1 / 2 / 3」。

两例只是结构和推理边界示范；不视为已发生的实测发现，也不自动提供统计、实验或实施方案。

## 4. 专业推理反例

1. **“Logo 更醒目、占位更小”**：视觉显著性与几何尺寸不同，可以通过对比、布局和视觉层级同时改善。原则上合理；是否达成识别目标仍需场景和证据。只有要求同一 Logo **在完全相同维度与条件下**尺寸同时增加和减少，才是逻辑矛盾。
2. **“零招募预算、30 名独立用户”**：不能据此断言不可能，可能有合法的现有用户招募渠道。需查明样本独立性、参与者权益、渠道权限和时间限制；未知时应说明关键条件尚待核实。
3. **“NPS 增长 8 点或平均满意度超过 4 分，未达标惩罚用研”**：整体目标可能合理；NPS、均值满意度和每个用户必须打分是不同命题。需核对基线、量表、抽样、团队可控因素与权责边界。若要求未经采集便伪造结果，则该造假要求原则性不可接受。
4. **“80 个功能全部首屏可见，同时保持 90% 留白，禁止滚动、折叠、隐藏”**：提示可能的空间/可辨识性冲突；但在视口、每个入口的定义、最小可辨识尺寸及布局边界未知时，不能直接证明绝对不可能。先标注方案条件待确认/疑似矛盾；有必要的几何和可用性边界证据后再升级。

这些是分析示范，不是实际访谈、实验结果或普遍强制标准。

## 5. 边界与独立交接

本 Skill 不制定完整研究计划、访谈问卷、产品方案、施工或开发任务，也不执行验收。需要更深入的方法引导、研究设计或方案决策支持时，可建议另开对话使用 **User Experience Decision Advisor（用户体验决策顾问，UXDA）**，Skill ID 为 `ux-decision-advisor`（[项目仓库](https://github.com/RagnTec/User-Experience-Decision-Advisor)）；这类推荐首次对用户出现时须提供全名、简介及仓库链接，不能只有“UXDA”缩写；该建议不意味着自动执行研究或实施工作。审查分类不能自动变成 UXDA 已接受的结论、实际数据或执行授权。
